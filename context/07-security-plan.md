# Security Implementation Plan

## Purpose

This document defines the security work required before Ghost AI exposes project, collaboration, artifact, and AI features to external users.

The plan follows the existing boundaries:

- Clerk is the identity source.
- Express independently authenticates every protected API request.
- PostgreSQL stores project authorization and task metadata.
- Liveblocks owns active collaboration state.
- Vercel Blob stores saved canvas snapshots and generated specifications.
- Trigger.dev runs durable AI workflows.
- The worker is a separate trust boundary from the API and browser.

Security work is implemented in small feature units. Each unit must be verified before the next unit starts, and `context/06_progress-tracker.md` must reflect the actual state.

## Security Goals

1. A user can access only projects for which they are the owner or a collaborator.
2. A client cannot choose ownership, authorization, storage paths, task ownership, or worker identity.
3. Project data, Liveblocks rooms, Blob artifacts, and task records remain isolated across projects.
4. Untrusted prompts, graph content, Markdown, and model output cannot execute code or access arbitrary resources.
5. Expensive operations have abuse, cost, concurrency, and payload limits.
6. Production fails closed when secrets, origins, or integration configuration is invalid.
7. Security events are observable without logging credentials, tokens, prompts, graphs, or generated artifacts.

## Threat Model

The implementation must defend against these actors and failure modes:

- An unauthenticated internet client probing API routes.
- An authenticated user attempting to access another user's project by changing an ID.
- A collaborator attempting owner-only operations.
- A compromised browser or modified frontend request.
- Replayed, forged, or mismatched Trigger.dev callbacks.
- A client attempting to join an unauthorized Liveblocks room.
- A client supplying arbitrary Blob URLs or storage paths.
- Malicious project labels, descriptions, prompts, Markdown, or AI output.
- Automated abuse intended to exhaust AI provider cost, database capacity, Blob storage, or room-token issuance.
- An operator accidentally using development secrets, seed data, or permissive origins in production.

## Security Decisions

These defaults should be used unless a product decision explicitly changes them:

| Area | Decision |
| --- | --- |
| API authentication | Bearer Clerk session tokens. Do not add cookie-authenticated API mutations without an explicit CSRF design. |
| Identity | Derive the acting user only from verified Clerk auth. Never trust a user ID from the request body, URL, or client state. |
| Project access | Owner and collaborators can read and mutate project resources. Owner-only actions are collaborator management, archive, and delete. |
| Collaboration | Room IDs are derived from server-authorized project IDs. Clients cannot select arbitrary room identities. |
| Blob storage | Objects are private. Keys are generated by server integrations from validated project and artifact IDs. |
| Task ownership | A TaskRun is created by the API before dispatch and is bound to the project and verified requester. |
| AI output | Model output is untrusted and must pass a strict shared schema before it changes a room or creates an artifact. |
| Error responses | Return stable JSON error shapes without internal details or resource-enumeration signals. |
| Secrets | Use managed deployment secrets and one documented local source. Never commit or bundle server secrets. |

The following decisions must be confirmed before the related feature is implemented:

- Whether collaborators may start AI and specification tasks, or whether those operations are owner-only.
- Whether archived projects are read-only for all members.
- AI provider retention, training usage, regional processing, and sensitive-data handling.
- Project and user quotas for AI runs, room tokens, snapshots, and artifact downloads.
- Artifact retention and cleanup behavior when a project is deleted.
- Production frontend origin, API origin, and private-networking capabilities of the deployment platform.

## Phase 0: Security Baseline

Complete this phase before adding product endpoints or external integrations.

### Secrets and configuration

- Rotate any credential that has been shared outside the secure development or deployment environment.
- Remove duplicated database credentials from local configuration.
- Use managed secret storage for deployed API and worker environments.
- Add secret scanning to local hooks and CI.
- Validate `NODE_ENV` against an allowed set and reject unknown values.
- Require explicit production values for Clerk keys, database credentials, origins, and integration secrets.
- Reject production localhost, wildcard, malformed, or non-HTTPS origins.
- Ensure test and development credentials cannot be selected by production configuration.
- Refuse production database seed execution unless an approved, separately protected procedure exists.

### Authentication policy

- Keep Clerk middleware before route registration.
- Keep the API bearer-token contract and do not store session tokens in local storage or query parameters.
- Configure Clerk `authorizedParties` with exact frontend origins.
- Configure CORS with the exact frontend origin and only required methods and headers.
- Document the policy for unexpected authentication cookies or alternate authentication mechanisms.
- Verify Clerk issuer, audience, expiration, authorized party, and token type in integration tests.

### Deployment boundary

- Enforce HTTPS at the frontend, API, and worker entry points where applicable.
- Configure production SPA rewrites for `/`, `/editor`, `/sign-in/*`, and `/sign-up/*`.
- Restrict database connectivity to API and worker deployments.
- Keep worker credentials separate from browser and API credentials.
- Keep Blob objects private and expose only authorized application download paths.

## Phase 1: API Security Foundation

Primary locations: `apps/api/src`, `packages/shared/src`, and `apps/api/tests`.

### Request boundary

- Add one runtime validation library and keep shared request schemas in `packages/shared`.
- Define schemas for projects, collaborators, graph nodes and edges, prompts, task IDs, artifact IDs, and pagination.
- Reject unknown fields where practical.
- Add an explicit global JSON limit and smaller route-specific limits for prompts, graph payloads, and metadata.
- Validate node count, edge count, nesting, string lengths, and total serialized graph size.
- Return a consistent JSON response for malformed JSON and validation failures.
- Do not parse unnecessarily large request bodies before rejecting unauthenticated requests.

### Middleware and errors

- Add security headers at the API boundary and configure the frontend deployment edge with a compatible CSP.
- Keep `x-powered-by` disabled.
- Add a final error handler that returns redacted JSON and never exposes stack traces, SQL, provider responses, or secrets.
- Add request IDs and propagate them into logs, task records, and error responses where appropriate.
- Never log bearer tokens, full prompts, full graph payloads, generated Markdown, connection strings, or provider credentials.

### Abuse controls

- Add rate limiting by IP for public routes and by authenticated user for protected routes.
- Add project-level limits for concurrent AI runs, snapshots, room-token requests, and downloads.
- Return `429` with `Retry-After` for rate-limit failures.
- Configure proxy trust explicitly before using forwarded client IP headers.
- Add timeouts and response-size limits to all outbound HTTP requests.

### Required API tests

- Unauthenticated requests receive the documented `401` response.
- Malformed, expired, wrong-issuer, wrong-audience, and wrong-authorized-party tokens are rejected.
- CORS allows the configured origin and rejects unexpected origins.
- Preflight requests expose only the required methods and headers.
- Malformed JSON and oversized bodies return safe JSON errors.
- Rate-limited requests return `429` without leaking implementation details.
- Unexpected errors are redacted and correlated by request ID.

## Phase 2: Project Authorization

Primary locations: `apps/api/src/modules/projects`, `apps/api/src/modules/collaborators`, and `packages/database`.

- Create one reusable project authorization service rather than duplicating ownership checks in controllers.
- Provide explicit capabilities for read, project mutation, collaborator management, archive, and delete.
- Query projects using owner-or-collaborator predicates rather than fetching by ID and checking afterward.
- Recheck authorization inside transactions immediately before sensitive mutations.
- Never accept `ownerId`, `requestedById`, role, or collaborator identity as trusted request data.
- Return a non-enumerating `404` for missing or unrelated project IDs. A collaborator who can already access a project may receive `403` for an owner-only operation.
- Prevent the project owner from being inserted as a collaborator.
- Enforce safe state transitions for archived projects.
- Use database-generated or cryptographically secure identifiers for persistent resources.
- Keep authorization tests beside each module and maintain a shared authorization matrix.

For email-based collaborator lookup:

- Treat submitted email addresses as untrusted lookup input; normalize and validate them at the API boundary.
- Resolve an existing Clerk user server-side and persist only the immutable Clerk user ID.
- Do not create access, invitation records, or pending state for unknown emails.
- Rate-limit lookup and collaborator mutations separately from ordinary project reads, and cap each project at 100 collaborators.
- Keep Clerk profile enrichment separate from authorization; missing profile data must not grant or remove access.
- Do not log submitted email addresses, Clerk responses, or profile payloads.
- Record audit events for successful collaborator additions and removals without recording email addresses.

### Authorization matrix

| Operation | Owner | Collaborator | Unauthenticated |
| --- | --- | --- | --- |
| List owned or shared projects | Allow | Allow | Deny |
| Read project metadata | Allow | Allow | Deny |
| Edit project metadata | Allow | Allow, subject to product policy | Deny |
| Edit collaborative canvas | Allow | Allow | Deny |
| Manage collaborators | Allow | Deny | Deny |
| Archive or delete project | Allow | Deny | Deny |
| Read task status | Allow | Allow, if task belongs to project | Deny |
| Download project artifacts | Allow | Allow | Deny |

Test each operation with an owner, collaborator, unrelated user, missing user, deleted project, archived project, forged IDs, and cross-project IDs.

## Phase 3: Database and Artifact Protection

Primary locations: `packages/database/prisma`, `apps/api/src/integrations/blob`, and `apps/api/src/modules/specs`.

### Database

- Add `Spec` and `TaskRun` models from the approved architecture.
- Add indexes for project task history and active task lookup.
- Make `triggerRunId` unique when present.
- Enforce valid task state transitions in application services.
- Use transactions for TaskRun creation, dispatch identifiers, Spec replacement, and collaborator changes.
- Add bounded connection-pool settings, acquisition timeouts, and graceful shutdown.
- Use separate database credentials or roles for API and worker workloads where feasible.

### Vercel Blob

- Generate `canvas/{projectId}.json` and `specs/{projectId}/{specId}.md` server-side.
- Do not accept arbitrary URLs, object keys, or provider references from browser input.
- Prefer canonical object keys over attacker-controlled URLs. If provider URLs remain in Prisma, treat them as server-generated references only.
- Recheck project membership for every artifact read, download, replacement, and deletion.
- Use short-lived signed URLs or authorized backend streaming.
- Set safe content types and `Content-Disposition` values.
- Prevent path traversal and cross-project key substitution.
- Bound snapshot and artifact sizes.
- Sanitize Markdown and reject unsafe URL schemes before rendering it in the browser.
- Define cleanup and retention behavior for replaced specs and deleted projects.

### Artifact tests

- A user cannot read another project's snapshot or specification by changing an ID.
- Arbitrary external URLs and path traversal inputs are rejected.
- Signed download links expire and cannot be used for another artifact.
- Stored Markdown cannot execute script or unsafe links in the frontend.
- Repeated saves and spec replacements are safe and consistent.

## Phase 4: Liveblocks Collaboration

Primary locations: `apps/api/src/integrations/liveblocks`, `apps/api/src/modules/collaboration`, and `apps/web/src/features/collaboration`.

- Derive room IDs from authorized project IDs.
- Check project membership before issuing a room token.
- Bind the token identity to the verified Clerk user ID.
- Issue the smallest required room permissions.
- Use short token lifetimes and rate-limit token issuance.
- Do not trust a client-provided project-to-room mapping.
- Validate graph updates before applying server-generated AI changes.
- Define maximum room payload and update sizes.
- Test owner, collaborator, unrelated-user, expired-token, and cross-room access.

## Phase 5: Trigger.dev and AI Workflows

Primary locations: `apps/api/src/modules/ai-runs`, `apps/api/src/modules/specs`, `apps/api/src/integrations/trigger`, and `apps/worker/src`.

### Task integrity

- Create a `TaskRun` in `QUEUED` state before dispatching a task.
- Generate idempotency keys on the server.
- Bind the task to the project, verified requester, internal task ID, and Trigger run ID.
- Authenticate Trigger callbacks with the provider-supported signature mechanism.
- Reject unsigned, mismatched, stale, or replayed callbacks.
- Make retries and status transitions idempotent.
- Re-fetch and authorize task records before every status or artifact update.
- Authorize task-status reads through project membership.
- Bound task runtime, concurrency, retry count, payload size, and provider cost.

### Prompt and model-output safety

- Enforce prompt and graph-context length limits before dispatch.
- Treat graph labels, descriptions, and existing Markdown as untrusted data, not instructions.
- Use strict structured output schemas for nodes and edges.
- Reject oversized, malformed, duplicate, or invalid graph output.
- Prevent model-generated content from invoking arbitrary tools, fetching URLs, or changing unrelated projects.
- Validate generated Markdown before persistence and rendering.
- Define provider data retention, training usage, and sensitive-data policies.
- Add abuse detection for repeated prompts, excessive retries, and unusually expensive requests.

## Phase 6: Frontend and Browser Hardening

Primary locations: `apps/web/src`, frontend deployment configuration, and auth feature tests.

- Keep frontend route guards as navigation UX only; the API remains authoritative.
- Keep Clerk session tokens out of local storage, URLs, logs, and analytics payloads.
- Restrict redirect values to approved same-origin relative paths.
- Render user and generated content as text by default.
- Sanitize Markdown only when rich rendering is required.
- Reject `javascript:`, `data:`, and unsafe external URL schemes in rendered content.
- Configure CSP for Clerk, the API, Liveblocks, and approved Blob domains.
- Configure frame protection, HSTS, Referrer-Policy, Permissions-Policy, and X-Content-Type-Options at the deployment edge.
- Verify keyboard-accessible error states for auth failures, authorization failures, rate limits, and expired sessions.

## Phase 7: CI, Operations, and Assurance

- Add CI with `npm ci` and the committed lockfile.
- Run frontend builds, API tests, worker tests, Prisma validation, and migration checks.
- Add secret scanning and static analysis as required checks.
- Run dependency audits and review reachability before applying major-version changes.
- Pin supported Node and npm versions.
- Add staging security smoke tests for Clerk, CORS, CSP, Liveblocks, Blob, Trigger.dev, and database access.
- Add dependency update monitoring and a documented vulnerability response process.
- Use structured logs with request IDs and redaction rules.
- Record audit events for authentication failures, authorization denials, collaborator changes, destructive actions, task lifecycle changes, and artifact access.
- Define alert thresholds for repeated authorization failures, token failures, rate-limit hits, task replays, and AI cost anomalies.
- Document incident response, secret rotation, account compromise response, and artifact cleanup.
- Perform a pre-release threat-model review and an external security review before broad public launch.

## Implementation Order

1. Add this security plan and confirm the security decisions.
2. Harden environment validation, secret handling, errors, headers, limits, logging, and tests.
3. Implement project APIs with centralized membership and capability authorization.
4. Add `Spec` and `TaskRun` models with transactional state handling.
5. Implement Liveblocks room authorization.
6. Implement private Blob snapshot and specification access.
7. Implement Trigger.dev task authentication, idempotency, and callback verification.
8. Implement AI input limits and structured output validation.
9. Add frontend CSP, safe rendering, redirect validation, and browser security tests.
10. Complete CI, deployment hardening, staging verification, and release review.

Do not expose a new product endpoint until it has authentication, authorization, input validation, limits, safe errors, safe logging, and negative security tests.

## Definition Of Done

Security work is complete for a feature unit when:

- Every access path has a documented trust boundary.
- The server derives identity and ownership from verified sources.
- Cross-project access tests fail safely.
- Inputs and outputs are validated at the boundary.
- Expensive operations have rate, size, time, concurrency, and cost limits.
- Secrets and sensitive user content are absent from logs and browser bundles.
- Production configuration fails closed.
- Unit, integration, and end-to-end tests pass.
- Relevant architecture and progress context files are updated.
